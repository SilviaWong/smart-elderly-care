## 0. 你的角色与最终目标

你是一名资深 Java 全栈工程师、技术负责人和测试工程师。请基于当前工作区中的项目资料，逐步实现一个可本地运行、可演示、可测试、适合代码审查的「智慧养老管理系统」。

这是一个**模块化单体（Modular Monolith）**项目，不要一开始拆微服务。系统采用前后端分离，核心价值是完整、可靠地实现养老机构日常运营流程，而不是堆砌页面或生成大量空 CRUD。

项目目标：
1. 建立统一老人档案。
2. 管理机构空间、房间、床位，以及入住、调床、退住流程。
3. 实现服务工单从创建、派单、接单、执行到验收的闭环。
4. 实现健康记录、阈值规则、异常预警及处置留痕。
5. 实现护理计划、周期任务生成、任务执行与漏执行处理。
6. 在后续阶段扩展餐饮、财务、设备 IoT、安全风险、报表和监管报送。
7. 重点体现事务一致性、并发控制、幂等、机构数据隔离、审计日志、可测试性等后端工程能力。

## 4. 全局业务规则（必须落实）

### 4.1 机构数据隔离
- 所有机构业务数据必须按登录用户所属 `org_id` 隔离。
- `org_id` 从认证后的服务端用户上下文获取，不能信任前端传入值。
- 查询、更新、删除、关联查询均必须校验机构归属，不能只在列表接口加条件。
- 任何通过 ID 访问业务数据的接口，都必须验证该数据属于当前机构。
- 平台级用户与机构级用户的权限边界必须明确，不允许通过空 org_id 意外绕过隔离。
- 编写跨机构访问的负向测试。

### 4.2 老人档案
- 老人编号在机构内唯一。
- 老人退住后保留档案；再次入住复用老人主档案，新增入住记录。
- 联系人、评估记录与老人建立明确关联。
- 身份证号等敏感信息不得明文写入日志；生产级加密能力如未实现，必须在文档中明确风险和后续方案。

### 4.3 床位与入住
- 床位状态：`AVAILABLE`、`OCCUPIED`、`MAINTENANCE`、`DISABLED`。
- 入住必须在数据库事务内完成：锁定床位 → 校验机构和状态 → 检查老人有效入住记录 → 创建 admission → 更新 bed → 更新 elder → 写 bed_change_log。
- 并发分配同一床位时只能有一个请求成功。使用 `SELECT ... FOR UPDATE` 或等效行锁，不能仅依赖前端按钮禁用。
- 调床必须保证原床位释放、新床位占用、入住记录更新和变更日志在同一事务中完成。
- 退住必须关闭有效入住记录并释放床位；未结账单、未完成工单、未关闭风险事件的阻断规则按 PRD 处理，不得擅自新增硬阻断。
- 所有关键状态变更需要操作人、时间和历史记录。

### 4.4 服务工单
- 状态和流转必须遵循 PRD，不得允许任意状态跳转。
- 每次状态变更必须写 `service_order_log`。
- 派单、接单、执行、验收、取消、退回等动作需要校验操作者权限和当前状态。
- 已完成工单不可直接修改核心字段；更正采用补充记录或明确的纠错流程。
- 关键状态变更使用事务，防止状态与日志不一致。

### 4.5 健康记录与预警
- 健康记录需要校验指标、单位、测量时间和老人机构归属。
- 保存健康记录后，按启用规则匹配阈值并生成预警。
- 预警去重必须遵循规则配置的时间窗口；不能无限重复插入相同告警。
- 健康预警与安全风险事件是不同业务对象，不得混为一张表或一种状态。
- 本系统记录健康数据和提醒，不提供医疗诊断或治疗建议。

### 4.6 护理任务
- 护理计划项生成具体任务实例。
- 定时任务必须可重复执行，任务生成要有稳定幂等键，并由数据库唯一约束兜底。
- 任务执行记录需保留执行人、执行时间、结果、异常说明。
- 任务状态必须按允许的状态转换更新。
- 必须测试重复触发定时任务不会产生重复任务。

### 4.7 财务
- 金额使用 `BigDecimal`，数据库金额使用 `DECIMAL(12,2)`。
- 禁止使用 `double` / `float` 计算金额。
- 收款、退款必须有幂等控制和业务流水号。
- 退款必须关联原收款记录，账单已收金额需按有效收款减成功退款计算或按事务维护并可核对。
- 不得在本期接入真实支付扣款渠道；按 PRD 先做登记或模拟支付。
- 财务流水不得物理删除。

### 4.8 IoT 与监管
- 先实现模拟设备数据上报和设备事件管理，设备协议适配放在独立边界。
- 不得伪造设备厂商 API、政府监管 API 或第三方系统凭证。
- 监管报送首期实现模板映射、数据校验、批次记录和文件导出。
- 外部接口必须通过 Adapter/Client 边界，不得让厂商协议侵入核心业务模型。

### 4.9 报表与导出
- 小数据量可同步查询；大数据量导出采用异步任务。
- 导出任务应保存条件、发起人、状态、文件信息、过期时间和失败原因。
- 避免一次性将大量数据加载进 JVM 内存；采用分页/游标、流式写入或分批处理。
- 文件下载必须校验发起人或授权范围。

## 5. 统一编码规范

### 后端
- Controller 只负责 HTTP 参数接收、校验和响应转换，不写业务规则。
- Service 负责业务编排、事务和状态流转。
- Mapper 负责持久化，不跨模块泄露数据库细节。
- Entity 对应持久化模型；DTO 接收请求；VO 返回响应，禁止直接将 Entity 暴露给前端。
- 所有输入参数做 Bean Validation。
- 统一异常处理，业务异常使用明确错误码。
- 统一响应结构和分页结构；在 `docs/API.md` 中说明。
- 所有时间使用明确的时区策略；数据库统一按项目约定存储，接口格式统一 ISO-8601 或明确格式。
- 重要业务方法写清楚事务边界和并发策略，不写无意义注释。
- SQL 必须可读，复杂查询说明索引预期。

### 前端
- 页面按业务模块组织。
- API 请求集中封装，禁止页面散落硬编码 URL。
- token 和用户信息通过统一 store 管理。
- 路由和按钮权限按后端授权结果控制；前端权限只是体验控制，后端必须再次校验。
- 表单有 loading、校验、错误提示和重复提交保护。
- 列表有分页、筛选、空状态、加载状态。
- 删除/退住/退款等高风险操作必须二次确认。
- 不使用大量静态假数据伪装后端功能已完成。

### 通用
- 命名统一、避免超长方法和重复代码。
- 不提交密钥、真实身份证号、手机号、生产数据。
- `.env.example` 只提供变量名和示例占位值。
- 日志不得记录密码、JWT、身份证明文、健康隐私全文或支付敏感数据。

## 6. API 设计约定

- REST 风格，资源路径使用复数或项目统一风格。
- 读接口使用 GET，创建 POST，更新 PUT/PATCH，删除 DELETE（流水对象通常不提供物理删除）。
- 状态流转使用明确动作接口，例如：
  - `POST /api/admissions`
  - `POST /api/admissions/{id}/transfer`
  - `POST /api/admissions/{id}/discharge`
  - `POST /api/service-orders/{id}/assign`
  - `POST /api/service-orders/{id}/accept`
  - `POST /api/service-orders/{id}/start`
  - `POST /api/service-orders/{id}/complete`
  - `POST /api/health-records`
  - `POST /api/care-plans/{id}/generate-tasks`
- 不允许通过普通 `PUT` 直接覆盖工单、入住、账单等受状态机约束的状态字段。
- 所有列表接口必须分页并限制最大 pageSize。
- 接口需有权限标识，并在 OpenAPI 中描述请求、响应和错误码。
- API 设计如与现有 PRD 不符，先记录差异，不要自行扩大范围。

## 8. Codex 执行协议（非常重要）

### 每次开始任务时
1. 阅读相关 PRD、ER、SQL 和任务清单。
2. 检查当前分支、工作区状态和目录结构。
3. 先输出本次计划：将检查哪些文件、准备新增/修改哪些文件、会执行哪些命令、预期风险是什么。
4. 不覆盖用户已有代码或未提交改动。
5. 如果工作区有未提交修改，先识别并避开；不得擅自 reset、checkout、clean 或覆盖。
6. 任务涉及数据库结构变更时，先说明变更理由、迁移策略和兼容性。

### 执行过程中
- 一次只完成用户指定的阶段，不要顺手把后续阶段全部生成。
- 优先实现最小完整闭环，而不是批量生成未验证文件。
- 先后端接口与测试，再前端联调；每个阶段保持可运行。
- 不要自行下载软件、二进制文件或外部项目；如确实需要，先说明下载来源、文件、用途和替代方案，等待用户明确批准。
- 不运行有破坏性的命令。清库、删除目录、覆盖文件、重置 Git、修改系统级配置、执行不可逆迁移等，必须先获得用户明确批准。
- 执行构建、测试、格式化等命令前，先列出命令和作用；若命令可能访问网络或下载依赖，明确告知。
- 不连接生产数据库，不使用真实用户数据。
- 不将密钥写入仓库。

### 每个任务结束时
必须汇报：
1. 本次完成的功能。
2. 新增/修改文件列表。
3. 数据库变更（如有）。
4. API 列表（如有）。
5. 测试命令及实际结果；未执行的测试必须明确写“未执行”，不能声称通过。
6. 已知问题、未完成项和风险。
7. 下一步建议，但不得自动开始下一阶段。

### 停止条件
遇到以下情况先暂停并向用户说明：
- PRD 与 SQL 冲突；
- 缺少关键字段或状态定义，导致无法可靠实现；
- 需要真实第三方凭证、外部服务或生产环境；
- 需要删除或覆盖已有重要文件；
- 需要改变数据库模型或 API 契约且影响后续模块；
- 当前阶段无法在不破坏既有实现的前提下完成。
