# 智慧养老管理系统 — 产品需求文档（PRD）

- 文档版本：V1.0
- 产品形态：B/S 管理平台（前后端分离）
- 前端：Vue.js + Element Plus（本次实现建议 Vue 3）
- 后端：Spring Boot 3.2.8
- 数据库：MySQL 8.0
- 架构：模块化单体
- 文档定位：可用于需求评审、数据库设计、接口设计与迭代开发的项目基线

## 1. 项目概述

### 1.1 项目背景
养老机构日常运营涉及老人档案、入住床位、护理服务、健康监测、餐饮、收费、设备、安全事件和监管报送等业务。若依赖纸质登记、Excel 或多个独立系统，容易出现信息重复、床位状态不一致、服务过程不可追溯、健康异常响应不及时、费用核对困难等问题。

本系统建设统一的养老机构运营管理平台，对老人从入住、日常照护、健康记录、服务执行到退住结算的过程进行数字化管理，并为管理人员提供统计分析能力。

### 1.2 产品目标
1. 建立统一的老人主档案，形成老人基本信息、联系人、健康信息和入住历史的关联视图。
2. 实现机构、楼栋、房间、床位的资源管理及入住/退住闭环。
3. 实现服务工单的创建、派单、执行、验收和评价闭环。
4. 支持健康指标记录、阈值规则、异常预警和处置留痕。
5. 支持护理等级、护理计划、周期任务生成与执行记录。
6. 支持餐饮订餐、膳食禁忌与餐次管理。
7. 支持费用项目、账单、收款、退款和对账基础流程。
8. 支持设备台账、设备数据接入、设备告警和设备事件追踪。
9. 支持安全风险事件的上报、处置、复核和归档。
10. 提供经营统计、业务报表和监管数据导出能力。

### 1.3 本期范围与边界
**纳入范围**
- 系统组织与权限管理
- 老人档案管理
- 入住与床位管理
- 服务与工单管理
- 健康管理
- 护理计划与执行
- 餐饮管理
- 财务管理
- 设备与物联网
- 安全与风险事件
- 数据统计与报表
- 监管报送（先做可配置导出，不假定已对接政府平台）

**暂不纳入**
- 医疗诊断、处方、电子病历和医保结算
- 真实硬件厂商协议适配（先提供模拟接入/API 接入边界）
- 政府监管平台真实接口联调（需取得当地接口规范和授权）
- 在线支付渠道真实扣款（本期先做支付流水登记/模拟支付）
- 多机构集团级 SaaS 计费与租户自助开通
- 原生 iOS/Android App（先做响应式 Web/H5 页面）

### 1.4 成功指标（建议验收口径）
- 老人档案关键字段完整率 ≥ 95%
- 床位状态与有效入住记录一致率 = 100%
- 工单全流程状态可追溯率 = 100%
- 护理任务执行记录可追溯率 = 100%
- 健康预警从数据入库到生成预警的处理时间：常规场景 ≤ 5 秒
- 费用账单金额与明细汇总一致率 = 100%
- 所有关键业务操作具备操作人、操作时间和状态变更记录

## 2. 用户角色与权限

### 2.1 角色定义
| 角色 | 主要职责 | 典型权限 |
|---|---|---|
| 平台/机构管理员 | 机构基础配置、用户、角色、权限、全局参数 | 机构内全部管理权限 |
| 院长/运营主管 | 查看运营数据、审批关键业务、监督服务质量 | 业务查看、统计、审批 |
| 入住接待人员 | 老人建档、入住办理、床位调整、退住办理 | 老人档案、入住床位 |
| 护理主管 | 护理等级、护理计划、任务分配、质量检查 | 护理计划与任务 |
| 护理员 | 接收并执行护理任务、记录服务情况 | 分配给本人/班组的任务 |
| 医护/健康管理员 | 健康指标录入、预警处置、健康档案维护 | 健康管理、风险协同 |
| 服务调度员 | 服务项目维护、工单派单、进度跟踪 | 服务工单 |
| 餐饮管理员 | 菜单、餐次、膳食要求、订餐 | 餐饮管理 |
| 财务人员 | 费用项目、账单、收款、退款、对账 | 财务管理 |
| 设备管理员 | 设备台账、设备绑定、设备事件处理 | IoT 设备 |
| 家属/联系人 | 查看授权老人有限信息、服务进度（后续扩展） | 仅授权范围只读 |
| 监管人员 | 查看或接收监管报送数据（后续扩展） | 指定报表只读 |

### 2.2 权限原则
- 采用 RBAC：用户—角色—权限。
- 所有业务数据默认按 `org_id` 隔离。
- 员工用户仅能访问所属机构；家属端需通过老人授权关系控制数据范围。
- 财务、健康、身份信息属于敏感数据，接口返回遵循最小必要原则。
- 删除优先采用逻辑删除；账单、收款、退款、健康记录、工单等业务流水禁止物理删除。
- 管理员权限不能绕过关键业务状态校验。

## 3. 业务对象与核心规则

### 3.1 组织与空间
- 机构（Organization）为数据隔离边界。
- 机构下可配置楼栋、楼层、房间、床位。
- 床位状态：`AVAILABLE` 空闲、`OCCUPIED` 已入住、`MAINTENANCE` 维修、`DISABLED` 停用。
- 床位必须属于一个房间；房间必须属于一个楼栋。
- 同一床位同一时刻最多存在一条有效入住记录。

### 3.2 老人档案
老人档案是全系统核心主数据，老人编号在机构内唯一。档案包含：
- 基础信息：姓名、性别、出生日期、证件类型/号码、手机号、地址、照片。
- 紧急联系人：姓名、关系、电话、是否主要联系人。
- 健康概况：血型、过敏史、慢病史、用药说明、饮食禁忌、行动能力备注。
- 评估信息：自理能力、护理等级、认知/风险评估结果（本系统仅记录评估结果，不替代专业诊断）。
- 状态：`PENDING` 待入住、`IN_HOUSE` 在住、`DISCHARGED` 已退住、`ARCHIVED` 已归档。
- 老人档案不因退住删除；再次入住时新建入住记录，复用老人主档案。

### 3.3 入住与退住
入住流程：
1. 查询/创建老人档案。
2. 完成入住评估与合同信息登记。
3. 选择空闲床位。
4. 服务端在事务中锁定床位记录并再次校验床位状态。
5. 创建入住记录，更新床位状态为已入住，更新老人状态为在住。
6. 写入床位变更记录。

退住流程：
1. 发起退住申请，登记退住日期、原因和经办人。
2. 检查未结账单、未完成工单、未关闭风险事件（可配置是否阻断）。
3. 完成费用结算或登记待结算。
4. 关闭入住记录，释放床位，更新老人状态。
5. 写入床位变更记录和操作日志。

约束：
- 床位分配必须使用数据库事务；并发分配使用 `SELECT ... FOR UPDATE` 或唯一约束兜底。
- 不允许将维修/停用床位分配给老人。
- 入住日期不得晚于退住日期。
- 同一老人同一时间不能有两条有效入住记录。

### 3.4 服务工单
工单来源：人工创建、护理任务转工单、设备告警转工单（后续可扩展）。
工单状态：
`PENDING_ASSIGN` 待派单 → `ASSIGNED` 已派单 → `ACCEPTED` 已接单 → `IN_PROGRESS` 执行中 → `PENDING_CONFIRM` 待验收 → `COMPLETED` 已完成。
异常状态：`CANCELLED` 已取消、`REJECTED` 已拒绝、`RETURNED` 已退回。
规则：
- 每次状态变更写入工单流转记录。
- 派单、接单、完成等动作需校验操作者权限。
- 工单完成需填写执行结果；是否需要验收由服务项目配置决定。
- 已完成工单不可直接编辑核心内容；更正通过补充记录实现。

### 3.5 健康管理
- 健康记录按老人、指标类型、测量时间记录。
- 指标类型包含血压、心率、体温、血氧、血糖、体重等，具体单位由指标配置定义。
- 阈值规则支持低于下限、高于上限、区间外等判断。
- 健康记录入库后匹配启用规则，命中时生成健康预警。
- 同一老人、同一指标、同一规则在设定时间窗口内可去重，避免重复告警。
- 预警状态：`OPEN` 待处理、`PROCESSING` 处理中、`RESOLVED` 已处理、`IGNORED` 已忽略。
- 健康预警与安全风险事件分开建模：预警表示指标异常；风险事件表示已经发生或疑似发生的安全事件。

### 3.6 护理计划与任务
- 护理等级可配置，例如一级/二级/三级护理；等级名称与服务内容由机构配置。
- 护理计划绑定老人、护理等级、起止日期和制定人。
- 计划明细定义护理项目、执行频率、执行时间窗口、责任班组/人员。
- 系统按计划生成护理任务；任务需具备幂等键，防止定时任务重复生成。
- 任务状态：`PENDING` 待执行、`IN_PROGRESS` 执行中、`COMPLETED` 已完成、`MISSED` 漏执行、`CANCELLED` 已取消。
- 执行记录保存执行人、执行时间、结果、异常说明。

### 3.7 餐饮管理
- 维护菜品、餐次、菜单和老人膳食偏好/禁忌。
- 老人可按日期、餐次订餐；订单保存下单时菜品名称、价格快照。
- 取消规则按餐次截止时间配置。
- 过敏/禁忌信息必须在订餐和配餐页面显著提示；系统不自动作医疗营养判断。

### 3.8 财务管理
- 费用项目：床位费、护理费、餐费、服务费、其他费用。
- 账单由账单主表和账单明细组成，明细保存计费期间、数量、单价、金额快照。
- 金额字段统一使用 `DECIMAL(12,2)`，禁止使用浮点数。
- 收款支持现金、银行转账、线上支付（本期可登记模拟渠道）。
- 退款必须关联原收款记录，保存退款原因、审批人和退款流水。
- 账单状态：`DRAFT` 草稿、`UNPAID` 未支付、`PARTIAL` 部分支付、`PAID` 已支付、`CANCELLED` 已取消、`OVERDUE` 已逾期。
- 收款接口需支持幂等号，避免重复入账。
- 账单金额 = 明细金额合计；已收金额 = 有效收款金额 - 已成功退款金额。

### 3.9 设备与物联网
- 设备台账记录设备编号、类型、厂商、型号、安装位置、状态。
- 设备可绑定老人或空间（床位/房间），绑定关系记录有效期。
- 设备数据记录原始值、标准化值、单位、采集时间、接收时间。
- 设备事件记录离线、低电量、异常读数、SOS 等事件。
- 首期支持模拟设备数据上报接口；真实协议适配作为独立适配层，不将厂商协议写入核心业务服务。

### 3.10 安全与风险事件
- 风险类型示例：跌倒、走失、突发不适、设备 SOS、其他。
- 事件包含发生时间、地点、老人、严重等级、描述、上报人、处理负责人。
- 状态：`REPORTED` 已上报、`ASSIGNED` 已分派、`PROCESSING` 处理中、`PENDING_REVIEW` 待复核、`CLOSED` 已关闭。
- 处理过程形成时间线；关闭需填写处理结论。
- 高等级事件可要求主管复核。

### 3.11 报表与监管报送
- 经营看板：在住人数、床位总数、床位使用率、待处理工单、护理任务完成率、健康预警数、当月收入。
- 业务报表：入住/退住、床位使用、工单、护理执行、健康记录、账单收款、设备状态、风险事件。
- 支持按日期、楼栋、护理等级、状态等筛选。
- 大数据量导出采用异步任务：创建导出任务→后台分页/游标处理→生成文件→下载；记录发起人、条件、文件地址、过期时间和状态。
- 监管报送首期提供字段映射、数据校验、Excel/CSV 导出、报送批次和结果登记；不虚构政府平台 API。

## 6. 核心业务流程

### 6.1 老人入住
建档/选择老人 → 入住评估 → 选择床位 → 并发锁定床位 → 创建入住单 → 更新床位/老人状态 → 生成入住相关费用（可选）→ 完成。

### 6.2 调床
发起调床 → 校验目标床位可用 → 事务锁定新旧床位 → 关闭旧床位占用关系 → 更新入住单当前床位 → 记录调床历史 → 完成。

### 6.3 工单处理
创建工单 → 派单 → 员工接单 → 执行 → 上传结果 → 验收（如需）→ 完成 → 评价。

### 6.4 健康预警
录入/接收健康数据 → 校验指标和单位 → 保存健康记录 → 匹配启用规则 → 生成或合并预警 → 指派处理人 → 处置记录 → 关闭/忽略。

### 6.5 护理任务
制定护理计划 → 计划明细配置周期 → 定时任务生成实例 → 分配执行人 → 执行签到/结果录入 → 完成/漏执行 → 主管查看完成率。

### 6.6 账单收款
选择老人/入住记录 → 选择计费期间 → 生成账单及明细快照 → 确认账单 → 收款登记 → 更新账单已收/未收状态 → 对账。

## 8. 数据与接口要求

### 8.1 通用数据字段
业务表建议统一包含：
- `id`：BIGINT 主键
- `org_id`：机构 ID（系统级表可为空）
- `created_by`、`created_at`
- `updated_by`、`updated_at`
- `deleted`：逻辑删除标识（仅适用于允许逻辑删除的主数据）
- `version`：乐观锁版本号（并发更新场景）

### 8.2 API 约定
- RESTful JSON API，统一前缀 `/api/v1`。
- 列表接口支持 `pageNum`、`pageSize`、筛选条件。
- 统一响应：`code`、`message`、`data`、`traceId`。
- 统一异常处理；参数校验失败返回明确字段错误。
- 状态变更接口采用动作语义，如 `/admissions/{id}/discharge`，不允许前端直接任意修改状态字段。
- 收款、入住、调床、任务生成等关键操作需幂等或事务保护。

## 9. 非功能需求

### 9.1 安全
- Spring Security + JWT 或等效认证机制。
- 密码使用 BCrypt/Argon2 哈希存储，不保存明文。
- 敏感字段脱敏展示；证件号等敏感字段按需要加密存储。
- 文件上传校验扩展名、MIME、大小，文件存储不直接暴露本地路径。
- 关键操作审计：登录、权限变更、入住、退住、收款、退款、风险事件关闭。
- 防止越权访问：每个查询和更新均校验 `org_id` 和数据权限。

### 9.2 性能与可用性（建议目标）
- 常规列表查询 P95 ≤ 1 秒（测试数据量与部署资源需明确）。
- 普通业务写操作 P95 ≤ 1.5 秒。
- 运营看板聚合查询应使用索引、缓存或汇总表，不在每次请求中全表扫描。
- 报表导出异步执行，避免 HTTP 请求长时间占用线程。
- 数据库连接池、慢 SQL 日志、应用日志和接口耗时监控。

### 9.3 数据一致性
- 入住、调床、退住、收款、退款等使用事务。
- 重要状态流转写业务流水表。
- 金额使用 DECIMAL；时间统一存储为 DATETIME，约定服务器时区。
- 业务流水不可物理删除。
- 定时任务必须幂等，失败可重试。

### 9.4 备份与恢复
- MySQL 定期全量备份，结合 binlog 做时间点恢复能力。
- 文件存储与数据库备份策略一致。
- 定期演练恢复流程；仅有备份文件不等于具备可恢复能力。

## 10. 验收标准（核心用例）

1. 同一床位被两个并发请求同时分配时，只允许一个请求成功。
2. 老人入住成功后，床位状态为 OCCUPIED，老人状态为 IN_HOUSE，且存在唯一有效入住记录。
3. 退住成功后，入住单关闭、床位释放、老人状态更新；未结费用按配置阻断或提示。
4. 工单每次状态变化均产生流转记录；非法状态跳转被拒绝。
5. 健康数据命中阈值后生成预警；重复数据在去重窗口内不重复创建同类预警。
6. 护理计划重复执行生成任务时，不产生重复任务。
7. 账单明细汇总金额与账单总额一致；重复收款请求不会重复入账。
8. 退款必须关联原收款，退款金额不能超过可退金额。
9. 设备解绑后，新数据不得错误关联到已失效的老人绑定关系。
10. 风险事件关闭必须填写处理结论，关键级别事件需复核。
11. 导出任务能够记录创建人、筛选条件、执行状态和文件有效期。
12. 不同机构用户无法读取或修改其他机构业务数据。

## 12. 设计假设与待确认事项
以下信息在原始资料中未明确，当前按可实现的通用方案设计，进入真实业务前需确认：
1. 机构是单院独立部署，还是多机构 SaaS；当前数据库按 `org_id` 多机构隔离设计。
2. 家属端是否作为独立门户；当前只预留联系人授权关系，不实现家属账号完整流程。
3. 健康指标的阈值是否需要按年龄、性别、疾病、设备来源动态配置；当前采用机构级规则。
4. 护理等级、护理频次和任务时间窗口由机构自定义。
5. 收费模式、计费周期、押金、优惠、滞纳金、发票规则需由实际机构确认。
6. IoT 厂商协议、设备数据格式、设备身份认证方式需按厂商资料适配。
7. 监管报送字段、编码、数据格式和接口由属地监管部门规范决定。
8. 用户个人信息、健康数据和监控数据的合规要求需结合部署地区法律法规评估。
